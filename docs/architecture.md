# アーキテクチャ決定事項

## 通信方向

| 対象データ | 方向 | 理由 |
|---|---|---|
| セキュリティ設定・ログイン履歴・更新状態 | クライアント→ホスト(Push) | CloudSecure等がREST APIを無効化することがあり、
  ホスト側の受信APIに影響を与えないため |
| 死活監視 | ホスト→サイト(Pull) | サイトがダウンしている間はクライアント側の送信処理自体が
  動かないため、外形監視は独立させる必要がある |

## 認証

- サイトごとに個別の連携キーを発行(全サイト共通キーにしない)
- 生キーをリクエストに載せず、HMAC-SHA256署名をヘッダーで検証する

## クライアント側のアダプタパターン

対応セキュリティプラグインごとに `Kagemiru_Adapter` インターフェースを実装した
アダプタクラスを用意する。コアは有効なプラグインを自動検出し、該当アダプタのみ
実行する。

- 対応プラグインを増やす際はアダプタを1つ追加するだけで済む
- 複数のセキュリティプラグインが同一サイトに併用されていても、検出されたアダプタを
  すべて実行しペイロードに含められる
- WordPress標準関数(`get_plugin_updates()`等)で取得できる情報(更新状態)は
  アダプタに含めず、コア側の共通処理に寄せる

## 未確定・要調査

- CloudSecure WP Securityのログイン履歴・WAF検知履歴の実際の保存先
  (テーブル名/オプション名)は未確認。実機導入後に確認し、
  `kagemiru-client/includes/class-adapter-cloudsecure.php` を実装する
- SiteGuard WP Plugin等、追加対応プラグインのアダプタは今後追加
